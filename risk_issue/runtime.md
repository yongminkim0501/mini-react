# 컴포넌트 런타임·Hook 리스크·이슈

관련 코드: `src/runtime/` · 기획서: [phase2-01](../docs/phase2-01-h.md), [phase2-03](../docs/phase2-03-resolve.md) ~ [phase2-09](../docs/phase2-09-demo-page.md)

## RT-01

**목록 중간 삭제 시 포커스·DOM 상태가 다른 항목으로 넘어감** · 중간 · 확인됨

- **GitHub 이슈:** #10 (기존 DF-02/AP-04 이슈, 마일스톤 Phase 1 구현에 댓글로 기록)

- **현상:** `h()`와 `resolve`는 key를 넘기지만 diff는 인덱스 기반이다(DF-02). 목록 `[a, b, c]`에서 `a`를 지우면 diff는 `li[0]`의 내용을 `b`로, `li[1]`을 `c`로 고치고 `li[2]`를 지운다. `b`의 버튼에 포커스가 있던 상태에서 `a`를 지우면, 포커스는 같은 DOM 버튼에 남은 채 그 버튼이 `c`의 버튼이 된다(`xb` → `xc` 확인). 데모에서 우유를 지우면 Patch가 10건 정도 나온다.
- **영향:** 키보드 사용자는 포커스가 엉뚱한 항목으로 옮겨진다. 상태로 제어하지 않는 화면 상태(입력 중인 글자, 스크롤 위치, 애니메이션)도 다른 항목으로 넘어간다. 데모의 체크 상태는 상태로 제어되므로 화면은 맞다.
- **대응안:** key 기반 diff와 `MOVE` Patch (docs/diff.md 8장, AP-04). 그 전까지는 문서와 데모에서 한계로 안내한다.

## RT-02

**렌더링 오류 후 상태 값과 화면이 어긋남** · 중간 · 확인됨

- **GitHub 이슈:** #15 · 마일스톤 Phase 2 구현

- **현상:** `setState`는 칸의 값을 먼저 바꾸고 렌더링을 예약한다. 그 렌더링이 오류로 실패하면 `FunctionComponent`는 이전 화면을 유지하지만, 칸의 값은 이미 새 값이다. `setN(1)` 후 `n === 1`에서 오류가 나는 컴포넌트는 화면 `0`, `hooks[0].value` `1`로 남는다.
- **영향:** 기획서 04 4.5의 "hooks 배열은 오류 이전 상태로 남는다"와 다르다. 다음 렌더링이 성공하면 한꺼번에 반영되어, 사용자는 오류 이전에 한 동작이 늦게 나타나는 것처럼 본다. 함수형 업데이트는 화면에 없는 값을 기준으로 계산된다.
- **대응안:** `setState`는 값을 바로 쓰지 않고 칸에 대기 값(`pending`)으로 쌓은 뒤, 렌더링이 성공했을 때만 확정한다. 실패하면 대기 값을 버린다.

## RT-03

**무한 렌더링 중단 후 상태가 화면보다 앞서 있음** · 낮음 · 확인됨

- **GitHub 이슈:** #15 (RT-02와 함께) · 마일스톤 Phase 2 구현

- **현상:** 연속 업데이트가 100회를 넘으면 `scheduleUpdate`가 예약을 거절한다. 그 직전 `setState`가 값을 이미 바꿨으므로, deps 없는 effect에서 `setN(n + 1)`을 부르는 컴포넌트는 화면 `100`, 상태 `101`로 멈춘다. 오류는 콘솔에만 나온다.
- **영향:** 버그 상황에서만 생기지만, 멈춘 화면이 상태와 달라 원인을 찾기 어렵다.
- **대응안:** RT-02의 대기 값 방식으로 함께 해결된다. 중단 시 오류를 화면에도 보이게 한다(RT-05).

## RT-04

**h()로 만든 목록의 key 중복을 경고하지 않음** · 낮음 · 확인됨

- **GitHub 이슈:** #16 · 마일스톤 Phase 2 구현

- **현상:** `fromHtml`은 형제 사이 `data-key` 중복을 `DUPLICATE_KEY`로 경고하지만(HV-04), `h()`와 `resolve`는 확인하지 않는다. `h('ul', null, [h('li', { key: 'a' }), h('li', { key: 'a' })])`에서 경고 0건.
- **영향:** 지금은 인덱스 diff라 동작 차이가 없다. key 기반 diff를 도입하면 중복 key가 잘못된 재사용으로 이어진다.
- **대응안:** `resolve`가 요소 자식을 모을 때 key 중복을 찾아 개발 중 `console.warn`을 남긴다.

## RT-05

**렌더링·Hook 규칙 오류가 콘솔에만 보임** · 낮음 · 기획 리스크

- **GitHub 이슈:** #17 · 마일스톤 Phase 2 구현

- **현상:** 기획서 04의 현재 안대로 렌더링 오류는 이전 화면을 유지하고 콘솔에만 출력한다. 자식 컴포넌트에서 Hook을 부르거나 Hook 개수가 바뀌어도 화면에는 아무 표시가 없다. 첫 렌더링이 실패하면 데모 영역이 비어 있다.
- **영향:** 데모 시연에서 "자식 Hook 금지"를 보여주려면 개발자 도구를 열어야 한다.
- **대응안:** `FunctionComponent`에 `onError` 콜백을 두고 데모 디버그 패널에 마지막 오류를 표시한다.

## RT-06

**useEffect가 반영 직후 동기 실행되어 화면 그리기를 막음** · 낮음 · 기획 리스크

- **GitHub 이슈:** #18 · 마일스톤 Phase 2 구현

- **현상:** 기획서 07의 현재 안대로 effect는 DOM 반영 직후 같은 작업 안에서 실행된다(React `useLayoutEffect` 시점). effect 안의 `setState`도 마이크로태스크로 다음 렌더링을 예약하므로, 브라우저가 그리기 전에 렌더링이 이어진다.
- **영향:** 무거운 effect는 클릭 후 화면 반영을 늦춘다. "로딩 중"을 먼저 보여주고 effect에서 바꾸는 패턴은 중간 화면이 보이지 않는다.
- **대응안:** 필요하면 effect 실행을 `requestAnimationFrame` 이후로 미루는 옵션을 둔다. 지금 데모 규모에서는 문제없다.

## RT-07

**매 렌더링 전체 트리를 새로 만들어 diff의 같은 객체 건너뛰기가 동작하지 않음** · 낮음 · 기획 리스크

- **GitHub 이슈:** #19 · 마일스톤 Phase 2 구현

- **현상:** `resolve`는 렌더링마다 모든 요소 VNode를 새로 만든다. Phase 1 diff의 "같은 객체면 하위 비교 생략"이 Phase 2에서는 한 번도 적용되지 않고, 바뀌지 않은 하위 트리도 모두 비교한다. 자식 컴포넌트도 props가 같아도 매번 다시 실행된다.
- **영향:** 이번 과제 규모(Todo 수십 개)에서는 문제없다. 노드가 수천 개면 입력 한 글자마다 전체 비교가 일어난다.
- **대응안:** 자식 컴포넌트에 얕은 props 비교 캐시(`memo`)를 두고, props가 같으면 이전 결과 VNode 객체를 재사용해 diff가 건너뛰게 한다.

## RT-08

**자식 컴포넌트의 순수성은 강제할 수 없음** · 낮음 · 기획 리스크

- **GitHub 이슈:** #20 · 마일스톤 Phase 2 구현

- **현상:** 자식 컴포넌트의 Hook 호출과 props 수정은 막지만, 전역 변수 읽기·쓰기, 렌더링 중 DOM 직접 수정, 모듈 변수에 상태 보관은 막을 수 없다.
- **영향:** "상태는 루트에만" 규칙을 우회한 코드가 오류 없이 돌아가고 화면 갱신이 누락될 수 있다.
- **대응안:** 문서 규칙으로 안내하고 리뷰에서 확인한다. 데모 자식 6개는 props만 사용한다.
