# 개인별 이슈 입력과 Claude 피드백 · v0.2

`issue-ym/` 등 승인된 사용자 디렉터리에 Markdown을 작성해 저장소 브랜치에 push하면 GitHub 이슈로 한 번 등록한다. Claude API는 현재 팀원의 기존 이슈·PR을 비교해 의견을 남긴다. 중복·통합 후보·작업 충돌이 있으면 관련 이슈들을 조정 이슈 하나에 모은다.

이 디렉터리는 입력함이다. 등록 후 상태·담당·댓글·검토·종료는 GitHub에서 관리하며 파일과 양방향 동기화하지 않는다. Copilot을 사용하지 않는다. Claude API 호출에는 등록한 API 계정의 사용량이 발생한다.

## 입력 형식

`.github/ax-issue-intake.json`의 sources에 `디렉터리: GitHub 계정`을 등록한다. 현재 `issue-ym: yongminkim0501`이다. 별칭은 로그인명과 달라도 된다. 팀원 추가 시 collaborator 등록과 이 매핑을 둘 다 반영한다.

예: `issue-ym/textarea-value.md` 또는 그 하위 디렉터리의 `.md` 파일. 첫 `---` 블록은 **JSON 형식**으로 작성한다. 일반 YAML 문법 전체를 지원하지 않는다. 추가 라이브러리 없이 JSON을 엄격히 검사하기 위한 계약이다.

```markdown
---
{
  "id": "ym-textarea-value-001",
  "title": "dirty textarea의 Patch 후 value 불일치",
  "type": "bug",
  "severity": "mid",
  "areas": ["patch"],
  "milestone": 2
}
---
## 기대 동작
Patch 후 textarea.value와 목표 VNode가 일치한다.

## 실제 동작
화면에 사용자가 입력한 이전 값이 남는다.

## 재현 방법
실제 확인한 입력과 명령·테스트 경로를 적는다.

## 관찰 커밋
확인한 전체 커밋 SHA. 모르면 미확인.

## 완료 조건
- [ ] dirty textarea의 값이 목표 텍스트와 일치한다.
- [ ] 기존 폼 처리 회귀 테스트가 통과한다.

## 파급 범위
검증 페이지 실제 영역의 textarea와 이력 이동.
```

위 예시는 형식 안내이며 이미 등록한 이슈 #6과 중복되므로 그대로 제출하지 않는다.

- `id`는 같은 사용자 디렉터리 안에서 유일한 3~80자 영문 소문자·숫자·하이픈이다. 파일명을 바꿔도 id는 유지한다.
- 제목은 200자 이하. type은 bug·feature·debt·risk·docs 중 하나, areas는 영역 지도에서 하나 이상, milestone은 열린 마일스톤의 실제 번호다.
- bug·risk는 severity high·mid·low가 필수다.
- 모든 유형은 `## 완료 조건`, `## 파급 범위`가 필요하다. 모르는 필수 내용은 `미확인`으로 적고 사람이 ready 여부를 판단한다.

| 유형 | 추가 필수 제목 |
|---|---|
| bug | 기대 동작, 실제 동작, 재현 방법, 관찰 커밋 |
| feature | 필요성, 범위, 의존 관계 |
| debt | 현재 타협, 타협의 영향, 개선 촉발 조건, 재검토 담당자 |
| risk | 리스크 영향, 수용 이유, 리스크 담당자, 완화책, 재검토 조건, 재검토 기한 |
| docs | 잘못되거나 빠진 내용, 대상 사용자 |

파일은 24 KB 이하, 전체 입력 파일은 100개 이하, 한 실행의 새 등록은 10개 이하로 제한한다. 제한 초과·잘못된 형식·중복 id·필수 라벨 누락은 등록 전에 실패시킨다. source 파일 안의 `<!-- ax-` 표식은 예약되어 사용할 수 없다.

## push와 중복 방지

활성화 후 이 저장소 브랜치의 `issue-*/` 변경 push에서 실행한다. 외부 fork의 push나 이슈·댓글 자체는 실행 이벤트가 아니다. 코드는 기본 브랜치의 검토된 자동화만 checkout하며, 입력 브랜치의 코드를 실행하지 않는다. 입력 파일은 GitHub API로 데이터만 읽는다.

push 브랜치의 최신 트리를 스캔하므로 재실행·파일명 변경·같은 내용을 다른 브랜치에 병합해도 id가 같으면 새 이슈를 중복 생성하지 않는다. GitHub Actions 봇이 만든 이슈의 출처 표식과 내용 해시를 확인한다. 출처 id가 같은 파일의 내용을 바꾸면 자동 덮어쓰기하지 않고 중단한다. 등록 이후 수정·추가 설명은 GitHub 이슈에서 하고, 별개 제출은 새 id를 쓴다. 파일 삭제로 이슈를 닫지 않는다.

동시에 들어온 push는 같은 queue에서 처리한다. GitHub가 대기 실행을 합칠 수 있어 매 실행에서 최신 입력 트리 전체를 읽는다. 서로 다른 브랜치에서 같은 id의 다른 내용을 제출하면 덮어쓰기 대신 충돌로 중단한다.

## 팀원 확인과 비교 자료

GitHub collaborator API를 매 실행에서 확인한다. push 사용자와 입력 소유자가 현재 collaborator여야 등록할 수 있다. 기존 이슈·PR과 댓글·리뷰도 현재 collaborator의 자료만 Claude에 전달한다. API 오류는 팀원으로 간주하지 않는다. 소유자가 권한을 잃으면 그 입력은 처리하지 않는다.

자동 등록 이슈는 작성자가 GitHub Actions 봇인지, 출처 표식에 기록한 소유자가 현재 collaborator인지 확인한다. 일반 사용자가 본문에 같은 표식을 붙여도 봇 작성자로 인정하지 않는다. 이 출처 표식은 비밀·인증 토큰이 아니라 신뢰한 워크플로의 등록 기록이다. 저장소 코드·워크플로를 수정할 수 있는 악의적 팀원까지 격리하는 보안 경계는 아니다.

비교 대상은 저장소 전체 마일스톤의 열린·닫힌 팀 이슈와 PR이다. 본문을 자르거나 일부 후보를 점수로 골라 신규라고 단정하지 않는다. 팀원이 남긴 일반 댓글·PR 리뷰·리뷰 댓글도 읽고, 열린 PR의 파일 목록과 API가 제공하는 patch를 전달한다. 자동 조정 이슈와 봇 댓글은 자기 피드백 순환을 피하려고 원본 증거에서 제외한다.

본문·댓글·PR 자료가 합계 200 KB를 넘으면 **AI 분석 대기**로 남긴다. 대형·바이너리 변경으로 GitHub가 patch를 제공하지 않는 경우에도 완전한 코드 충돌 분석을 보장하지 않는다. AI는 불확실하면 판단 보류를 제안해야 한다. 모든 자료를 읽어도 판단 정확도와 인젝션 방어가 완전히 보장되지는 않는다.

## 피드백 위치와 조정 이슈

1. 등록 이슈에 Claude 댓글: 신규 / 중복 / 통합 후보 / 작업 충돌 / 판단 보류, 근거, 관련 이슈·PR 링크와 다음 행동 제안.
2. 중복·통합 후보·충돌에는 조정 이슈 생성: 원본 2~3개 이상의 번호와 사용자 멘션, 근거와 사람이 결정할 사항. 같은 실행에서 연결된 관계는 하나의 집합으로 묶고, 같은 참여 집합에 대한 재실행은 기존 조정 이슈를 재사용한다. 다른 실행에서 부분적으로 겹치는 조정 집합까지 자동 통합하지는 않는다.
3. 각 연결 이슈·PR에 조정 이슈 링크를 댓글로 남긴다. 같은 실행의 재시도에서는 같은 봇 댓글을 수정해 중복 알림을 줄인다.
4. Actions 실행 Summary에 파일 → 등록 이슈 → AI 결과 → 조정 이슈 링크를 남긴다.
5. 칸반에서는 이슈 카드를 열어 같은 댓글을 본다. 프로젝트 자동 추가는 아래 별도 설정이 필요하다.

API 키 누락·실패·출력 검증 실패·입력 한도 초과는 성공 판정으로 바꾸지 않고 대기 댓글을 남긴다. Secret·원문 API 오류 응답은 출력하지 않는다. 설정을 고친 뒤 Actions 실행을 재실행하면 등록 이슈를 재사용한다. 성공한 원본 입력은 반복 분석하지 않으며 사람의 재검토는 기존 이슈에서 진행한다.

## 권한 분리

- 등록 job: 이슈 생성 권한. ready·담당 지정 필드를 입력 계약에서 받지 않는다.
- 분석 job: GitHub 읽기 권한과 해당 step에만 Claude API 키. 모델에 도구·셸·GitHub 쓰기 토큰을 전달하지 않는다.
- 게시 job: Claude 키 없음. JSON 형식·분류·후보 번호를 검증한 뒤 고정된 댓글·조정 이슈만 게시한다. 후보 작성자의 collaborator 상태와 본문 변경도 재확인한다.
- AI의 자유 텍스트는 멘션·외부 링크·HTML을 제한해 표시한다. 실제 팀원 멘션과 GitHub 링크는 검증된 메타데이터로 만든다.
- 실제 통합·PR 병합·이슈 종료·ready·담당 배정·리스크 수용은 계속 사람의 역할이다.

## 최초 활성화

기본 상태는 비활성이다. 기본 브랜치가 현재 `main`이므로 자동화 파일·스크립트·설정이 main에 반영되어야 한다. PR의 기능 브랜치에만 파일이 있는 동안 활성화하지 않는다.

1. 이 변경을 검토하고 기본 브랜치에 반영한다.
2. 기존 라벨과 함께 새 `ax:intake` 라벨을 만든다. 재사용 스크립트 전체를 다시 실행하면 기존 라벨에서 중단하므로 이번 추가분만 실행한다.

   ```sh
   gh label create ax:intake --repo yongminkim0501/mini-react --color 5319e7 \
     --description '개인별 입력 디렉터리에서 자동 등록된 이슈·AI 조정 이슈'
   ```

3. Repository → Settings → Secrets and variables → Actions에 **ANTHROPIC_API_KEY** Secret을 등록한다. 키를 이슈·채팅·파일·로그에 적지 않는다.
4. 선택적으로 **AX_TRIAGE_MODEL** 변수를 현재 사용하는 Claude API 모델 ID로 지정한다. 기본은 분류용 `claude-haiku-5-5`다. 모델의 계정 사용 가능 여부와 실제 호출은 키 설정 후 검증한다.
5. **AX_ISSUE_INTAKE_ENABLED=true** Repository variable을 설정한다.
6. Projects #13 → Workflows → Auto-add to project에서 저장소 mini-react, 필터 `is:issue label:"ax:intake"`를 켠다. 항목 추가 시 Status=Backlog도 설정한다. 기존 전체/AX/Phase 1 칸반과 마일스톤 필터는 유지한다. 이 자동 추가 설정을 켜기 전에는 새 이슈를 프로젝트에 수동 추가해야 한다.
7. 새 입력 한 건을 push하고 생성 이슈·Claude 댓글·Actions 요약·프로젝트 유입을 확인한다. 기존 이슈와 겹치는 입력은 원본별 링크와 조정 이슈의 중복 방지까지 확인한다.

중지는 AX_ISSUE_INTAKE_ENABLED를 false로 바꾼다. 기존 이슈·댓글·프로젝트 카드는 유지한다. API 분석을 재실행하면 추가 사용량이 발생할 수 있다.

## 검증

```sh
node --test scripts/ax/issue-intake.test.mjs
```

외부 API를 모킹해 협업자 제한·출처·중복 등록·전체 원문 입력·예산 초과·임의 참조 거부·그룹 조정·재시도·권한 회수·텍스트 출력 제한을 검사한다. 이 테스트는 실제 Claude 판단 품질이나 GitHub Actions 배포 검증을 대신하지 않는다.

공식 API 기준: [Claude Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [모델 목록](https://platform.claude.com/docs/en/models/overview), [GitHub 비신뢰 입력](https://docs.github.com/en/actions/concepts/security/script-injections).
