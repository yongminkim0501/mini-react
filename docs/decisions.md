# 결정 기록

형식: 날짜 · 결정 · 이유 · 검토한 대안. 최신 항목이 아래에 온다.

## 작업 A: 측정용 히트맵 탐색기 (stack 엔진)

### D-A01 · 2026-11-10 · 분기 기준을 `feat/phase2-components-hooks`로 함

- **결정:** 브랜치 `feat/scenario-a-lab-harness`를 `feat/phase2-components-hooks`에서 분기한다.
- **이유:** 지시는 "없으면 develop에서 분기"였다. 그런데 `origin/develop`에는 엔진 코드(`src/core`, `src/runtime`)가 없다. Phase 1 병합이 #26에서 되돌려졌고 AX 도구만 남아 있다. 측정 대상이 없으므로 사용자에게 확인했고, phase2 브랜치에서 분기하라는 답을 받았다. 브랜치 이름은 사용자가 지시했다.
- **검토한 대안:** develop에서 분기한 뒤 phase2 병합(충돌 위험, AX 파일 혼입), Phase 1/2가 develop에 병합될 때까지 대기.

### D-A02 · 2026-11-10 · 계측 훅은 전역 하나로 등록하는 모듈로 둠

- **결정:** `src/runtime/instrument.ts`의 `setInstrumentation({ onRenderStart, onRenderEnd, onCommit })`. `FunctionComponent`의 `mount`/`update`에서만 부르고, 등록되지 않으면 바로 반환한다. 훅에서 난 오류는 삼킨다.
- **이유:** 루트가 두 개(히트맵, 진행 바)라도 측정 도구는 한 곳에서 받아야 한다. 이벤트에 루트 인스턴스를 넘기므로 어댑터가 라벨로 구분한다. 엔진 동작에는 영향이 없다. 기존 테스트 260개가 그대로 통과하고, 미등록·오류 시 동작은 새 테스트 3개로 확인했다.
- **검토한 대안:**
  - 기존 인스턴스 `onCommit` 재사용: 렌더링 시작/끝이 없고 Phase 2 디버그 패널이 이미 쓰고 있다.
  - 인스턴스 필드로 훅 등록: 루트마다 따로 연결해야 하고 Fiber 엔진과 모양을 맞추기 어렵다.
  - 엔진을 고치지 않고 `diff`·`applyPatches`를 감싸기: ES 모듈 바인딩이라 바깥에서 바꿀 수 없다.

### D-A03 · 2026-11-10 · 렌더와 커밋 구간 정의

- **결정:**
  - 렌더 = `renderStart`→`renderEnd`. 루트 함수 실행 + `resolve`(자식 실행)다.
  - 커밋 = `renderEnd`→`commit`. `diff` + `applyPatches`(또는 실패 시 재마운트)다.
  - `onCommit`은 DOM 반영 직후, effect 실행 전에 부른다.
  - "업데이트당 렌더 시간"은 둘의 합이다.
- **이유:** stack 엔진에서는 diff가 렌더 뒤에 따로 돈다. 두 구간을 나눠 두면 Fiber와 비교할 때 어느 단계가 줄었는지 보인다. effect를 빼야 엔진 비용만 잴 수 있다.
- **검토한 대안:** effect까지 포함, diff를 렌더 쪽에 포함.

### D-A04 · 2026-11-10 · 테스트 러너는 기존 vitest

- **결정:** `lab/lab.test.js`를 vitest로 돌린다(`vite.config.ts`의 include에 `lab/**/*.test.js` 추가).

### D-A05 · 2026-11-10 · 격자 크기: 날짜 100열 고정, 카테고리 행 수로 조절

- **결정:** 셀 수 = 카테고리 수 × 100(날짜)이다. 슬라이더는 2,000~20,000, 1,000 단위다(20~200행).
- **이유:** 열 수가 고정이면 CSS grid 열 정의가 하나로 끝나고 셀 크기(8px)도 일정하다. 셀 수는 행 수에 정비례하므로 측정 결과를 해석하기 쉽다.
- **검토한 대안:** 정사각형에 가깝게 열·행을 함께 바꾸기. 크기마다 레이아웃이 바뀌어 비교 조건이 달라진다.

### D-A06 · 2026-11-10 · 입력·클릭 지연을 두 기준으로 기록

- **결정:**
  - 기본 지표는 지시대로 `event.timeStamp`→(반영 커밋 이후 첫 rAF)다.
  - 스크립트 입력은 "예정 시각 기준"(`*FromIntendedP95`)도 함께 기록한다.
- **이유:** 스크립트가 `dispatchEvent`로 만든 이벤트는 실제로 보낸 순간에 `timeStamp`가 찍힌다. 메인 스레드가 막혀 타이머가 늦게 실행되면 그 대기 시간이 기본 지표에서 빠진다. 사람의 실제 입력은 하드웨어 시각이 찍혀 대기 시간이 포함되므로, 예정 시각 기준이 사람이 느끼는 지연에 더 가깝다.
- **검토한 대안:** 예정 시각 기준만 쓰기(지시와 다름), 기본 지표만 쓰기(막힘이 가려짐).

### D-A07 · 2026-11-10 · 반영 여부는 커밋 직후 DOM을 읽어 판정

- **결정:**
  - 입력: `#echo`의 `textContent`가 입력값과 같아지면 반영으로 본다. 그보다 앞서 들어온 입력도 함께 반영된 것으로 본다.
  - 클릭: `#detail`의 `data-seq`가 클릭 전 값보다 커지면 반영으로 본다.
- **이유:** 측정 도구가 앱 상태나 엔진 내부를 읽지 않는다. 화면에 실제로 나온 것을 기준으로 해서, Fiber 엔진이 입력을 건너뛰거나 묶어도 같은 방식으로 잴 수 있다. 같은 셀을 두 번 클릭해도 `seq`가 올라가므로 구분된다.
- **검토한 대안:** 앱이 `window`에 상태를 노출(앱 수정 필요), 셀 id 비교(같은 셀 재클릭 시 오판).

### D-A08 · 2026-11-10 · 실행마다 히트맵 루트를 다시 마운트

- **결정:** 매 실행 전에 `unmount` → 같은 props로 새 루트를 `mount`하고 500ms 기다린다.
- **이유:** 재생성 버튼이 시드를 올리므로 실행마다 데이터가 달라진다. 같은 시작 상태에서 반복해야 평균이 의미가 있다. 셀 선택은 실행마다 시드(`seed*1000+run`)를 고정한다.
- **검토한 대안:** 상태를 그대로 두고 반복(데이터가 달라짐), 페이지 새로고침(자동 실행 흐름이 끊김).

### D-A09 · 2026-11-10 · Long Task 지연 전달 처리

- **결정:** `stop()`은 종료 시각을 정한 뒤 200ms 기다린다. 그동안 프레임·커밋·지연 기록은 닫고, 구간 안에서 시작한 Long Task만 센다.
- **이유:** `PerformanceObserver`는 항목을 늦게 전달한다. 처음에는 기다리는 동안 다른 기록도 계속 쌓여서 진행 바 fps가 63으로 나왔다(60Hz 화면). 고친 뒤 정상 범위로 돌아왔다.
- **검토한 대안:** 기다리지 않음(마지막 Long Task 누락).

### D-A10 · 2026-11-10 · percentile은 선형 보간

- **결정:** 정렬 후 `(p/100)*(n-1)` 위치를 선형 보간한다(PERCENTILE.INC와 같다).
- **이유:** 표본이 20개(키 입력 20회) 정도로 적을 때 최근접 순위 방식보다 값이 덜 튄다.
- **검토한 대안:** 최근접 순위.

### D-A11 · 2026-11-10 · 셀 스타일은 문자열 `style` + `class`

- **결정:** 배경색은 `style="background:hsl(...)"`, 흐림·강조·선택은 class로 표현한다.
- **이유:** 엔진의 `style`은 문자열만 받고 객체는 버린다(Phase 2 결정). 값이 그대로면 문자열도 같으므로 diff가 바뀐 셀만 고친다.
- **검토한 대안:** style 객체(엔진 수정 필요), 흐림도 style에 넣기(검색할 때마다 style 문자열 전체가 바뀜).

### D-A12 · 2026-11-10 · lab은 Vanilla JS(ES 모듈), 엔진은 Vite로 가져옴

- **결정:** `lab/`은 `.js` + JSDoc으로 쓰고, 엔진은 `../src/runtime/index.ts`를 import한다. 페이지는 Vite가 서빙·빌드한다(`vite.config.ts`에 입력 추가).

### D-A13 · 2026-11-10 · 시나리오 클릭 대상은 인덱스로 바로 찾음

### D-A14 · 2026-11-10 · 진행 바 위치는 시간 기반, 프레임마다 setState

- **결정:** `useEffect` 안 rAF 루프에서 `(now - start) % 2000`으로 위치를 계산해 `setProgress`한다. CSS 애니메이션·transition은 쓰지 않는다.
- **이유:** CSS 애니메이션은 컴포지터에서 돌아 메인 스레드가 막혀도 움직인다. 시간 기반이면 끊김이 "위치 점프"로 보이고, 진행 바 루트의 커밋 간격이 곧 애니메이션 프레임 간격이 된다.
- **검토한 대안:** 프레임마다 고정량 증가(멈춘 만큼 느려져 끊김이 덜 보임).

### D-A15 · 2026-11-10 · 인공 부하는 Cell 렌더 안에서, 기본 0

- **결정:** `?cellCost=ms`면 `Cell`이 렌더될 때마다 `burn(ms)`를 부른다. 기본은 0이다.
- **이유:** Fiber에서 끊어 실행할 단위가 컴포넌트이므로, 부하도 컴포넌트 렌더 안에 있어야 비교할 수 있다. `burn`은 결과를 반환하고 sink에 섞으며, 루프 안에서 시계를 읽지 않는다.
- **검토한 대안:** diff 단계에 부하 추가(엔진 수정 필요).

## 작업 A-2: 모니터링 화면 전환, 측정 환경 고정, stack 기준선

### D-A16 · 2026-11-10 · 화면을 "서버 × 최근 100분 p95 지연" 장애 대응 화면으로 바꿈

- **결정:** 행은 서버, 열은 분, 셀 값은 p95 지연(ms), 태그는 `버전 상태`(예: `deploy-1742 err-503`)다. 시드로 장애를 심는다.
  - 평소에는 낮은 지연 + 잡음, 드물게 `err-504`.
  - 14:40부터 3분마다 12개 묶음으로 `deploy-1742` rolling deploy.
  - 배포를 받은 서버의 약 35%에서 2~6분에 걸쳐 지연이 오르고 `err-503`이 난다.
- **이유:** 이전 화면은 태그가 셀마다 무작위라 검색에 의미가 없었다. 배포 버전·에러 코드는 시각마다 달라지는 값이라 셀 단위 매칭이 자연스럽다. 측정 특성(셀 단위로 강조가 갈림)은 그대로 유지된다.
- **검토한 대안:** 매장 × 날짜 매출(셀 단위 태그가 어색함), 행 단위 필터(시간·서버 위치 정보가 사라지고 비용 모양이 diff 방식에 좌우됨).

### D-A17 · 2026-11-10 · 검색은 행을 걸러내지 않고 셀 강조/흐림 유지

- **결정:** 매칭 셀은 테두리로 강조하고, 나머지는 흐리게 한다. 행은 그대로 둔다.
- **이유:** 이 화면에서는 시간·서버 위치 자체가 정보다. 배포가 계단식으로 번진 모양과 에러 시작 시점은 매칭되지 않은 칸이 제자리에 있어야 보인다(README에 적음).
- **검토한 대안:** 매칭 행만 남기기.

### D-A18 · 2026-11-10 · S2 검색어를 `deploy-1742 err-503`(19글자)으로 바꿈

- **결정:** 타이핑 시나리오는 20글자가 아니라 19글자를 친다.
- **이유:** 장애 대응자가 실제로 칠 검색어다. 20글자로 맞추려고 뜻 없는 글자를 붙이지 않았다. 지표는 키 입력당 평균·p95라 글자 수가 하나 달라도 비교할 수 있다.
- **검토한 대안:** 태그 형식을 20글자에 맞추기(부자연스러움), 의미 없는 글자 추가.

### D-A19 · 2026-11-10 · 화면 전환 전후 비교는 두 버전을 번갈아 실행해서 잼

- **결정:** 전환 전 커밋(`cdc43e4`)을 임시 worktree에서 다른 포트로 띄웠다. 같은 시간대에 전 → 후 순서로 10k·20k의 S2를 쟀다.
- **이유:** 같은 기기에서도 시간대에 따라 렌더 시간이 약 3배 차이 났다(10k 키 입력당 33ms vs 102ms). 시간을 두고 따로 재면 화면 변경 효과와 기기 상태가 섞인다.
- **검토한 대안:** 이전 측정값 재사용(기기 상태가 달라 비교 불가).

### D-A20 · 2026-11-10 · 기준 조건: 메인 20k, 보조 10k, cellCost 0

- **결정:** 페이지 기본 `size`를 20000으로 바꾼다. `cellCost`는 예비 옵션으로만 둔다.
- **이유:** 지시대로다. 20k는 stack에서 키 입력당 렌더가 이미 50ms를 넘어 인공 부하 없이도 문제가 드러난다.
- **검토한 대안:** 10k + cellCost.

### D-A21 · 2026-11-10 · 주사율 추정과 예산 기반 끊김 판정

- **결정:**
  - 시나리오마다 rAF 간격 90개의 중앙값으로 주사율을 추정한다.
  - 프레임 예산은 `1000/Hz`, 끊긴 프레임은 예산 2배 초과로 센다.
  - 60Hz ±3을 벗어나면 경고한다.
  - 페이지를 연 직후의 추정(HUD용)은 첫 마운트가 끝나고 1.5초 뒤에 한다.
- **이유:** 이 기기는 가변 주사율이라 60Hz와 120Hz를 오갔다. 고정 33ms 기준은 120Hz에서 끊김을 절반만 센다. 마운트 중에 재면 30Hz로 잘못 나오는 것을 확인했다.
- **검토한 대안:** 고정 16.7ms, 평균값으로 추정(긴 프레임 하나에 끌려감).

### D-A22 · 2026-11-10 · 시나리오마다 엔진별 워밍업 1회를 버림

- **결정:** 측정 반복 전에 같은 시나리오를 엔진마다 1회 돌리고 결과를 버린다. 결과에 `warmupDiscarded: 1`을 남긴다.
- **이유:** 첫 실행은 JIT와 스타일·레이아웃 캐시가 덜 데워져 느리다.
- **검토한 대안:** 페이지 로드 직후 고정 대기만 하기.

### D-A23 · 2026-11-10 · 교차 측정: 실행 단위로 엔진을 번갈아 돌림

- **결정:** `?engines=a,b`면 워밍업(a, b) 뒤에 run마다 a, b 순서로 돈다. 엔진을 바꿀 때는 두 루트를 모두 내리고 새 엔진으로 다시 만든다. 구현되지 않은 엔진은 건너뛰고 `skippedEngines`에 남긴다.
- **이유:** D-A19와 같은 이유로, 기기 상태 변화가 한 엔진에만 실리지 않게 한다. fiber가 아직 없어도 stack 측정이 막히지 않는다.
- **검토한 대안:** 엔진마다 페이지를 새로 열기(번갈아 돌리기 어려움), 구현 안 된 엔진에서 중단.

### D-A21a · 2026-11-10 · 주사율 추정을 "구간별 중앙값의 최솟값"으로 고침 (D-A21 보완)

- **검토한 대안:** 전체 중앙값 + 대기만 늘리기(느린 구간이 길면 여전히 틀림), 최소 간격 하나(잡음 하나에 흔들림).

### D-A21b · 2026-11-10 · 실행 중 주사율 변화를 진단값으로 기록 (D-A21 보완)

- **이유:** 이 기기에서는 사람 입력이 약 13초 없으면 rAF가 120Hz에서 30Hz로 떨어지는 것을 확인했다(2초 구간 중앙값이 8.4ms에서 33.7ms로 바뀜). 자동 측정에는 사람 입력이 없으므로 실행 도중에도 일어날 수 있다. 실행 중 추정은 끊김이 많은 시나리오(S4)에서 낮게 나오므로 판정 기준으로는 쓰지 않는다. 시스템 설정 변경(디스플레이 주사율 고정, Chrome 에너지 절약 끄기)은 사람이 해야 한다.
- **검토한 대안:** 실행 중 추정값으로 끊김 판정(끊김이 많을수록 기준이 느슨해짐), 측정 중 가짜 사람 입력 주입(측정 대상에 개입함).

### D-A21c · 2026-11-10 · 끊김 판정 예산을 "그 실행에서 관측한 주사율"로 바꿈 (D-A21b 수정)

- **결정:**
  - 실행마다 그 실행의 프레임 간격으로 주사율을 추정한다(30프레임 구간별 중앙값의 최솟값).
  - 그 값으로 예산을 정하고 끊김(예산 2배 초과)을 센다.
  - 실행 전 추정은 `environment.refreshHz`와 `preRunBudgetMs`로 남기고, 프레임이 없을 때만 판정에 쓴다.
- **이유:** 10k S1에서 실행 전 추정은 120Hz였는데, 실행 중 화면이 60Hz로 떨어졌다. 그 결과 정상적인 60Hz 프레임까지 모두 끊김으로 세서 182개가 나왔다. 걱정했던 연속 업데이트 시나리오(S4, 20k)에서도 관측값이 60/60/60으로 실행 전 추정과 같았다. 재생성 사이에 조용한 구간이 충분해서 관측값이 끊김에 끌려 내려가지 않았다. 이 문제가 드러나기 전에 잰 결과는 기준선에 쓰지 않았다.
- **검토한 대안:** 실행 전 추정 유지(주사율이 바뀌면 틀림), 둘 중 큰 값(60Hz로 떨어진 실행을 120Hz 기준으로 판정함).

### D-A21d · 2026-11-10 · 판정 주사율을 "실행 전체 프레임 중앙값"으로, 끊김에 1ms 여유 (D-A21c 수정)

- **결정:**
  - 실행마다 프레임 간격 전체의 중앙값으로 주사율(`refreshHzObserved`)과 예산을 정한다.
  - 끊김은 예산 × 2 + 1ms 초과로 센다.
  - 가장 조용한 30프레임 구간 기준 주사율과 3Hz 넘게 다르면 `refreshUnstable = 1`로 표시한다. 평균하면 주사율이 바뀐 실행의 비율이 된다.
- **이유:** D-A21c의 "가장 조용한 구간" 방식은 실행 중 주사율이 바뀌면 그중 가장 빠른 주사율을 고른다. 10k S1의 한 실행은 대부분 60Hz(프레임 중앙값 16.6ms)였는데 짧게 120Hz 구간이 있어서 120Hz로 판정됐고, 60Hz 프레임 151개를 끊김으로 셌다. 중앙값은 그 실행에서 가장 흔한 주사율을 따른다. 긴 프레임은 개수가 적어 중앙값에 영향이 작다(20k S4에서도 중앙값이 정상 프레임 쪽에 있었다). 1ms 여유는 16.6~16.8ms처럼 반올림된 정상 프레임이 120Hz 기준 경계(16.7ms)에 걸리지 않게 하기 위해서다. 그 전 결과는 기준선에 쓰지 않았다.
- **검토한 대안:** 프레임마다 주변 구간의 주사율로 판정(구현이 복잡하고 경계가 모호함), 주사율이 바뀐 실행 버리기(이 기기에서는 S1 대부분이 버려짐).

## 작업 B · Fiber 엔진

아래 B-0 기록은 구현 완료를 뜻하지 않는다. 세부 근거는 [B-0 설계 보고](codex/B0-design.md)에 있다. 승인 대기 항목은 적용하지 않았다.

### B01 · 2026-11-10 · 기준과 관문 분리

- **상태:** 사용자 지시 확인, 브랜치 생성 완료.
- **결정:** `baseline-stack` (`ef08734`)에서 `feat/fiber-engine`을 만들고 별도 worktree에서 작업한다. B-0은 문서만 작성한다. 푸시·PR 없이 보고 후 정지하고 B-1부터 관문마다 승인을 기다린다.

### B02 · 2026-11-10 · 엔진 연결은 기존 앱 팩터리 활용

- **상태:** 설계 제안, B-1 착수 승인 대기.
- **제안:** `lab/engine-adapter.js`에서 Fiber 팩터리·Hooks를 주입한다. 기존 VNode/h를 재사용하고 stack hookRuntime은 공유하지 않는다. stack에 공통 디스패처를 추가할 필요가 없다.

### B03 · 2026-11-10 · 새 데이터 업데이트의 Transition 표시

- **상태:** D-A27 예외 승인 대기, 미적용.
- **제안:** `lab/app/heatmap-app.js`의 onRegenerate 한 줄만 startTransition으로 감싼다. S4도 같은 버튼을 사용하므로 함께 적용된다. stack을 같은 세션에서 다시 측정하며 기존 태그·원자료는 보존한다.

### B04 · 2026-11-10 · 레인 경계와 두 번째 루트

- **상태:** 설계 제안.
- **제안:** Fiber 전용 실제 이벤트 핸들러 호출 범위는 Sync, startTransition 안은 Transition, rAF·타이머 등 그 밖은 Default로 둔다. try/finally로 복구한다. ProgressApp rAF는 Default이며 별도 특혜를 주지 않는다. B-2는 단일 레인·루트 순환, B-3는 전역 최고 레인 우선이다.

### B05 · 2026-11-10 · 기존 useMemo와 최적화 제외 범위

- **상태:** 해석 승인 대기.
- **제안:** 앱이 이미 사용하는 useMemo는 호환 Hook으로 구현한다. 새 React.memo·subtree bailout·key 기반 비교는 추가하지 않는다. 자식은 순수 함수, Hooks는 루트에서만 허용한다.

### B06 · 2026-11-10 · 단계별 시간의 비교 한계

- **상태:** 비교 기준 승인 대기.
- **근거:** stack Commit 수치는 diff를 포함하고 Fiber reconciliation은 Render에 속한다.
- **제안:** frozen stack 계측을 유지하고 Render+Commit 합계를 비교한다. 각 단계는 엔진별 구간임을 표시한다. Fiber는 양보를 포함한 경과 시간과 실제 작업 구간 합계·폐기 비용을 구분한다. 단계별 완전 동일 정의를 원하면 별도 frozen 계측 변경 승인이 필요하다.

### B07 · 2026-11-10 · Fiber 차등 테스트의 의미

- **상태:** 검증 설계 제안.
- **제안:** 기존 stack 테스트를 변경하지 않는다. Fiber용 행동 테스트를 추가해 DOM·이벤트·노드 재사용·form/SVG·정규화·Hooks를 비교한다. Fiber effect는 passive drain 후 단언하고, stack의 즉시 effect·내부 배열 단언까지 동일하다고 주장하지 않는다.

### B08 · 2026-11-10 · 중단 시 큐 보존과 순서 복원

- **상태:** B-3 설계 제안.
- **제안:** skipped lane과 그 뒤 적용된 action의 재생 순서를 보존한다. WIP 폐기가 committed 큐의 업데이트를 소비하면 안 된다. 함수형 합산뿐 아니라 대입 업데이트 혼합도 검증한다. 연속 Transition에서 작업은 합칠 수 있지만 action을 임의로 버리지 않는다.

### B09 · 2026-11-10 · 성능 목표는 실측으로 판정

- **상태:** 위험 기록, 구현 전 가설.
- **판단:** 5ms 양보는 단일 root 함수·데이터 계산·동기 Commit을 분할하지 못한다. bailout 없는 긴급 렌더도 큰 트리를 처리한다. 모든 Long Task 제거와 p95 1~2프레임 달성을 보장하지 않으며, 실패하면 실제 원인을 보고하고 범위 확장은 별도 승인받는다.

### B10 · 2026-11-10 · 측정 수명과 비교 환경

- **상태:** 측정 설계 제안.
- **제안:** root/attempt별 계측과 취소 상태, 시나리오 완료 시 대기 작업, S4 수신·커밋 횟수를 기록한다. 예정 시각 기준 지연은 유지한다. 측정 창 정의를 바꾸면 stack도 재측정한다. 과거 값 대신 동일 환경에서 교차 실행하며 주사율 변동을 함께 보고한다.

### B11 · 2026-11-10 · B-0 승인과 B-1 범위

- **결정:** 루트·host·text Fiber를 double buffer로 유지하고 순수 자식 함수는 반복 루프의 확장 프레임으로 처리한다. 펼친 host 결과끼리 인덱스로 비교한다. key는 stack과 같은 data-key 전파에만 쓰며 identity 매칭에 쓰지 않는다.

### B13 · 2026-11-10 · Render·큐·Commit 소유권

- **결정:** 새 DOM은 detached 상태에서 속성·자식을 구성할 수 있다. 재사용하는 DOM·핸들러는 Render에서 바꾸지 않는다. Commit은 삭제→새 subtree 삽입→속성/텍스트 갱신→current 교체 순서다. updater는 setter에서 실행하지 않고 Render에서 재생하며, 커밋 성공 때만 큐에서 소비한다. 실패 시 기존 current와 action을 보존한다.
- **제약:** Commit 중 DOM API 오류는 rollback할 수 없으므로 성공으로 보고하지 않고 예외를 전파한다. 자동 재마운트로 실패를 숨기지 않는다. 전체 subtree bailout은 추가하지 않는다.

### B14 · 2026-11-10 · passive effect의 예약과 수명

- **결정:** 정상 실행은 rAF 뒤 task에서 effect를 실행한다. 이는 paint 기회를 주는 예약이며 실제 물리적 paint 완료 보장은 아니다. 테스트는 명시적 passive drain으로 시점 차이를 구분한다. effect/cleanup 오류는 격리하며 unmount는 미실행 effect·예약 작업·이전 setter를 무효화한다.
- **결정:** 의존성 없는 effect가 상태를 계속 갱신하는 경우 기존 안전 기준처럼 100회 연속 갱신에서 중단한다. Fiber는 passive task에 걸쳐 세며 외부 업데이트에서 연속 횟수를 초기화한다. 거절한 action은 큐에 넣지 않는다.
