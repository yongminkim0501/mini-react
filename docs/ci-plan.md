# CI 도입안: 린트·단위 테스트

> 현재 배포 구조: AX는 앱 구현과 분리되어 `tools/ax/`의 전용 패키지로 검사한다. `npm ci --prefix tools/ax && npm run check --prefix tools/ax`를 사용한다. 아래의 앱 패키지·Vitest 측정값과 브랜치 구성은 이전 PR 작성 당시 기록이며 현재 AX의 의존성이 아니다. 앱 CI는 Phase 1 검토·도입 시 별도 구성한다. 자세한 복구 순서는 [AX 분리 문서](ax-isolation.md)를 따른다.

제공된 CI 도입안을 Markdown으로 정리한 저장소 적용 기준이다. 실제 도구 선택·측정값·미완료 항목은 [셋업 PR 검토 자료](ci-setup-pr.md)에 분리한다.

## 1. 목적과 범위

PR이 생성·갱신될 때마다 린트와 단위 테스트를 자동 실행하고, 실패하면 기본 브랜치에 병합되지 않게 한다. 에이전트의 테스트 통과 보고와 별개로 CI가 같은 기준으로 독립 검증한다. 완료 조건별 증거 중 기존 동작 유지의 근거로 CI 결과를 사용하되, 새 요구사항의 충족까지 자동으로 판정하지 않는다.

- 포함: PR·기본 브랜치 push의 린트·단위 테스트, 실패 시 병합 차단, 검사 설정 변경 보호
- 제외: 별도 통합·E2E 환경, 커버리지 기준, 배포, 성능 측정

AX 경량 도입안과 독립적으로 운영할 수 있으며 교차 리뷰, Refs 표기, 에이전트 skill 규칙과 함께 사용한다.

## 2. 구성 요소

| 요소 | 역할 | 위치 |
|---|---|---|
| 단일 검사 진입점 | 로컬·CI가 같은 린트·테스트 실행 | 패키지 스크립트 또는 Makefile |
| 워크플로 | PR·기본 브랜치 push 검사 | .github/workflows/ci.yml |
| 병합 차단 | 검사 실패·승인 없음이면 병합 금지 | Rulesets 또는 브랜치 보호 |
| 검사 보호 | 검사 설정 변경의 지정 담당자 리뷰 | .github/CODEOWNERS |

워크플로 파일만으로는 병합이 차단되지 않는다. 로컬 검사 → CI 재검사 → 사람 리뷰·병합 흐름을 구성한다.

## 3. 단일 검사 진입점

Node 저장소에서는 package.json의 lint·test·check로 구성한다. lint와 test가 실패하면 0이 아닌 종료 코드를 반환해야 한다. 경고만 출력하고 성공하는 설정은 피한다.

```sh
npm run lint
npm test
npm run check # lint 성공 후 test
```

PR 생성 전에 check를 실행하고 명령·결과·대상 커밋을 PR 본문에 기록한다. ax-submit-pr skill에도 반영한다. CI는 실패 원인을 구별하도록 lint와 test를 별도 job으로 실행한다.

## 4. 워크플로 설계

- 트리거: pull_request, 기본 브랜치 push
- 검사에는 pull_request_target을 사용하지 않는다. 비신뢰 PR 코드를 실행하는 검사와 쓰기 권한·Secret을 결합하지 않는다.
- permissions: contents: read
- concurrency: 같은 PR·브랜치의 이전 실행 취소
- timeout: lint 10분, test 15분
- job 이름은 lint·test로 고정한다. 이름 변경 시 필수 검사 설정도 바꾼다.
- 액션은 도입 시점의 고정 주 버전 태그를 쓰고 @main을 쓰지 않는다.
- 언어 설정·lockfile 기반 의존성 캐시로 전체 실행 5~10분 안쪽을 목표로 한다.

워크플로 전체의 paths 필터로 필수 검사를 건너뛰지 않는다. 영역별 실행을 나눠야 한다면 워크플로는 실행하고 job 수준 조건을 사용한다. 현재는 경로 필터 없이 검사한다.

## 5. 병합 차단 설정

기본 브랜치의 Rulesets 또는 브랜치 보호는 저장소 관리자가 설정한다. 에이전트는 이 셋업에서 원격 설정을 바꾸지 않고 PR에 설정 항목을 정리한다.

| 규칙 | 설정 |
|---|---|
| 필수 상태 검사 | lint, test |
| PR 필수 | 승인 1건 |
| 새 커밋 시 승인 취소 | 켬 |
| Code Owners 리뷰 필수 | 켬 |
| force push·브랜치 삭제 | 차단 |
| 브랜치 최신 상태 요구 | 처음에는 끔 |

병합 뒤 기본 브랜치가 반복해서 깨질 때 최신 상태 요구를 켜고, 부담이 크면 merge queue를 검토한다.

## 6. 검사 무결성

### 에이전트 규칙

- PR 생성 전 check를 실행하고 실제 결과를 첨부한다.
- 코드 원인을 고친다. 테스트 skip·삭제, 단언 완화, 린트 규칙 비활성화로 통과시키지 않는다.
- 테스트·린트 설정 변경이 필요하면 변경 전에 PR에 사유를 적어 담당자 승인을 받는다.
- 일상 구현 작업에서 CI 워크플로를 수정하지 않는다. 명시적으로 요청된 CI 셋업은 그 범위에서 수행한다.
- 기대값 변경은 기대 동작이 왜 바뀌는지 이슈의 완료 조건과 연결해 설명한다.

### CODEOWNERS

워크플로·CODEOWNERS·검사 진입점·lockfile·린트/테스트 설정 파일에 지정 담당자를 둔다. 셋업 초안의 담당자는 비워 두고 사람이 확정한다. 담당자 지정과 Rulesets의 Code Owners 리뷰 필수 설정이 둘 다 있어야 강제된다.

리뷰어는 삭제된 단언, 추가된 skip, 바뀐 기대값을 확인한다. CI 통과만으로 이 변경들의 타당성이 검증되지는 않는다.

## 7. 도입 시 주의

### 기존 린트 위반

기존 위반이 많으면 다음을 비교해 선택한다.

- 변경 파일만 검사: 빠르게 시작할 수 있지만 손대지 않은 파일의 위반은 남는다.
- 기준선: 도구가 지원할 때 기존 위반을 기록하고 새 위반만 실패시킨다. 기준선 파일도 검사 보호 대상이다.

기존 위반 정리는 type:debt로 영역별 등록한다. 위반이 없거나 적어 정리 가능한 경우 전체 검사도 검토하되 선택 근거를 PR에 명시한다. 도구에 없는 기준선 기능을 있는 것처럼 가정하지 않는다.

### 기존 CI가 있는 경우

상위 저장소의 CI를 먼저 확인하고 기존 것이 있으면 확장한다. 워크플로 단위 paths 필터로 skip하면 필수 검사가 대기로 남을 수 있다. 조건으로 건너뛴 job은 성공으로 보고되므로 적용 범위를 사람이 검토한다.

### 실패 처리

| 실패 | 처리 |
|---|---|
| 린트·테스트 실패 | 원인 코드 수정 후 push |
| 러너·네트워크·설치 실패 | 인프라 문제로 분류하고 사람이 1회 재실행 |
| 재실행 시 통과하는 테스트 | type:bug로 등록, 임시 skip은 사람 승인 후 |

실행 실패·미실행은 통과가 아닌 미확인이다.

## 8. 사람과 에이전트 역할

| 작업 | 사람 | 에이전트 |
|---|---|---|
| 언어·도구·린트 도입 방식 | 결정 | 현황·위반 수·선택지 제시 |
| 검사 명령·워크플로·CODEOWNERS | 셋업 PR 리뷰·병합 | 파일 작성·검사·PR 생성 |
| Rulesets·브랜치 보호 | 관리자가 설정 | 설정 목록만 정리 |
| CODEOWNERS 담당자 | 지정 | 초안은 비움 |
| 에이전트 규칙 | 확인 | AGENTS.md·skill 반영 |
| 일상 PR | 결과·테스트 diff 리뷰 | check 실행·원인 수정 |
| 인프라 실패 | 재실행 | 분류·보고 |
| 불안정 테스트·검사 설정 | skip/변경 승인 | 조사·사유 기록 |

## 9. 셋업 체크리스트와 도입 검증

파일 작성 완료와 원격 적용·보호 검증 완료를 구분하여 기록한다.

- [ ] 기존 CI 유무 확인
- [ ] 언어·린트·테스트 도구와 도입 방식 결정
- [ ] lint·test·check 명령 작성
- [ ] ci.yml과 의존성 캐시 작성
- [ ] CODEOWNERS 작성, 사람이 담당자 지정
- [ ] 셋업 PR 리뷰·병합
- [ ] Rulesets 설정
- [ ] AGENTS.md·ax-submit-pr CI 규칙 반영
- [ ] 아래 시나리오 검증

| 시나리오 | 기대 결과 |
|---|---|
| 린트 위반 PR | lint 실패, 병합 차단 |
| 실패 테스트 PR | test 실패, 병합 차단 |
| 검사 통과·승인 없음 | 병합 불가 |
| 검사 통과·승인 1건 | 병합 가능 |
| 승인 후 새 커밋 | 승인 취소·재승인 필요 |
| 워크플로 변경 PR | Code Owner 리뷰 요청 |
| 같은 PR 연속 push | 이전 실행 취소·최신 실행 유지 |
| 기본 브랜치 병합 | push CI 재실행·통과 |

검증용 PR은 사람이 확인하고 닫으며, 결과를 셋업 PR에 기록한다. 보호 설정이 없는 상태에서 로컬 실패 종료 코드만 확인한 것은 병합 차단 검증 완료가 아니다.

## 10. 셋업 PR의 필수 기록

저장소 조사 결과, 도구·도입 방식과 위반 수, 단일 진입점, 워크플로·캐시, 담당자가 빈 CODEOWNERS, 에이전트 CI 규칙, 미정 사항의 가정 목록을 포함한다. Rulesets는 실행하지 않고 설정 항목만 본문에 적는다. 기존 CI가 있으면 확장하고, 기존 위반을 피하려고 검사 기준을 약하게 만들지 않는다.
